# 访谈终止条件与第一个回复

## 为什么先定终止条件
访谈什么时候算完，要在开始前和用户说定，否则会无限追问，或过早收口。终止条件从契约定义推出，用户批准后记为 D-001；之后"能不能输出 spec""能不能定为基线"都按它判断。

## 推导规则
- 逐节对照契约定义（`contract-definition.md`）：第一节（理解资料、区分来源）→ T1、T5；第二节（可履约的承诺）→ T3；第三节（覆盖）→ T2；第四节（验收）→ T4；第五节（需求、设计、任务分工）→ T6；第七节（自检）→ T7；第六节（授权与变更）写进"输出状态"。
- 不机械套用数量限制（定义第五节）。首个项目 T01 的草案借用了 GitHub Spec Kit 的"开放问题不超过 3 个"和"拆里程碑、选技术"，读到定义后都删掉了。
- T2 的覆盖清单写成本项目的具体内容：点名本项目的每条端到端流程、关键对象的生命周期、可能的不变量、外部接入。

## T1–T7 模板（按项目改写后全文给用户）
- **T1 来源可追溯**：每条需求标来源类型和出处（D/F/S/A/Q）；推断与建议未经批准不写成已确认需求；不新增没有依据的功能、岗位、指标、审批或流程。
- **T2 覆盖完整**：问题、用户、目标、成功标准；本次范围、可选范围、明确不做；端到端流程（逐条列出本项目的主流程）；角色的决策权、执行权与交接；关键对象的生命周期（拒绝、修改、超时、冲突）；系统不变量（例："未经本人确认不进看板""Agent 不替人确认"）；数据含义、生产者、消费者、修改权；异常、降级、恢复（外部接入失败）；隐私与可见性（谁看谁、告知、保存期限）；未决问题、版本状态、变更规则。
- **T3 承诺可履约**：每条关键需求写触发与前置条件、负责人与输入、可观察行为、权限与禁止、失败/冲突/缺输入/缺证据时的处理、验收、上游依据；不出现无法判定的说法；系统控制不了的结果只写"支持，由人决定"。
- **T4 验收可独立判断**：写明验收方式、环境、周期、判定人、证据；指标写清口径、时间范围、有效输入、缺失值；自述、勾选、配置不能代替证据。
- **T5 缺口有处置**：实质性缺口（会改变目标、范围、权限、验收的）全部由用户拍板；其余记为假设或待决，写明影响和决定人；用户说"默认可行"的外部条件记为外部依赖假设，并写降级行为。
- **T6 分工清楚**：不写未决的技术选型、算法、里程碑、任务拆分；已批准的约束（如部署形态）保留并注明依据。
- **T7 自检与冷读**：契约定义第七节 7 问逐条通过；两个只看契约文件的子 Agent——设计者视角（阻塞问题为零）、验收者视角（验收条件全部可判、没有歧义项）。

**输出状态**：先交付"待确认草案 v0.1"；用户明确批准后才成为基线；用户可以随时喊停，未覆盖的部分以"假设/待决"写入。
