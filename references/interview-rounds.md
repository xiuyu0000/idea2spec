# 访谈轮：选题、质疑、挖掘、条目、审批台、反馈

`<desk>` 指审批台 skill interactive-approval-desk（开源：https://github.com/xiuyu0000/interactive-approval-desk）所在目录，本节按它的 v3.7.1 写。审批台自己的规则（字段形状、字数上限、自检项目）以它的 `round_template/README.md` 和 `references/` 为准；这里只写访谈怎么用它。

## 1 一轮的节奏
- 一轮 = Claude 在对话轮 Txx 发出审批台 Rxx → 用户填写、提交，说"反馈完成"（下一个对话轮）→ Claude 处理反馈，发出下一轮。
- 一轮 5–20 条，按主题分组。条目多不可怕，捆绑才可怕：首个项目 R07 有 20 条，按主题分组、标了"需要细看/可快速确认"，用户一次审完。审批台默认只显示每张卡简短的一层，并按字数预算自检；一个议题放不下就拆成两张卡。
- 首个项目的主题顺序（参考）：
  - **R01 用户目标与第一版范围**（12 条）：首先服务谁；现在最痛的事与代价；和现有工具的关系；用哪几项判断做成了；数据能否用于个人绩效；Agent 只提示不下结论；先给谁用；必做功能；关键流程做到哪一步；外部接入做到什么程度；明确不做；按多少人验收。
  - **R02 交付验收与协作规则**（15 条）：问题与代价草稿；上一轮评论的澄清；任务固定格式；谁确认完成；Agent 审核看什么、怎么表达；证据怎么保存；过程记录；优先级与依赖；忙闲不均；会议待办规则；目标层谁维护；拒绝或修改安排；无人回应；谁能看谁；软件版本。
  - **R03 进度风险与部署数据**（16 条）：消息放在哪；中间交付物节奏与验收；延误后重排；"时间"怎么测；进度与风险口径；风险信号发给谁；部署描述的含义；数据能否发给模型；登录与组织关系；试点前告知；保存期限；扩大范围的门槛。
  - **R04 签署**（15 条）→ **R05 定稿确认**（9 条）→ **R06 定稿前核对**（5 条）→ 基线 v1.0。
  - **R07 原型与 MVP 契约方案**（20 条）→ **R08 派生契约签署**（15 条）。

## 2 调研与质疑
用户请 Claude"沟通、质疑、挖掘"，是因为想法里可能有：思维的断裂、考虑不周全、对技术或概念的误解、脱离现实场景。对应的查法：

| 可能的问题 | 怎么发现 | 去哪找依据 | 首个项目的例子 |
|---|---|---|---|
| 思维断裂：目标和功能之间缺环节 | 画端到端流程，找没人负责的环节、没定义的状态与口径 | 项目材料、同类产品的流程 | 想"提示风险"，但没定义风险怎么算、发给谁、谁来判断是否成立 |
| 考虑不周：异常、冲突、缺输入、缺证据、角色缺位 | 每条流程走一遍正常/异常/缺证据三条路径；权限矩阵逐格过 | 冷读、同类产品 | 主管与本人意见冲突谁裁定；最高一级的人既是发起人又是裁定人时怎么办 |
| 技术或概念误解 | 查可靠性与可行性证据 | 论文、标准、官方文档 | LLM 当评判者与人的一致率约 80%（S-14）、会自信地给出错误内容（S-13）→ Agent 只给提示和依据，结论由人下 |
| 脱离现实 | 查真实世界的反应与教训 | 研究、厂商调查、新闻、法规 | 被监控的员工更易违规（S-01）；微软因个人行为视图被批评而改为组织汇总（S-02）；个人信息保护法的告知义务（S-08） |

规则：
- 质疑写成：你的想法 → 查到了什么（S-编号，置信度）→ 对本项目意味着什么 → 推荐做法与备选 → 不同意的话会怎样。
- 研究结论只是"启示"和推荐，由用户定。首个项目按同类产品做法推荐"时长数据只看 ≥5 人汇总"，用户否决，改为按个人统计、只对开发者可见（D-049）——这是用户的决定权，照写即可。
- 涉及法规写"一般理解，不是法律意见"。
- 来源写进 `registry/sources.md`：编号、标题与链接（付费墙注明经何处核对）、要点、置信（H/M/L，可分"结论/细节"）、首次使用的轮次；表头写核验日期。
- 每轮的调研简报写 `research/Rxx_evidence.md`（`templates/evidence_Rxx.md`），每个主题以"→ 启示"收尾。

## 3 挖掘
- **让用户讲真实案例与代价。** R01 问"现在最痛的是哪几件事"，列出候选痛点让用户勾选，并请他讲一个例子。首个项目里，用户讲了一个重点项目因为没有协作流程和过程记录、进度一再延误而失败、事后也无法复盘的经过（F-002），它成了范围取舍的锚。
- **从用户陈述的事实推出可能需要的能力**，作为下一轮的提议交用户拍板，不自行加入范围。F-002 推出了优先级、前置依赖、负载分布、待办截止时间、中间交付物与复盘（R02-07..R02-10）。
- **关键名词第一次出现时用例子复述含义。** R03-07 里用户说的"各项目花的时间"，指的是使用平台的耗时，Claude 理解成了员工在各项目上的工作时间，用户只好在反馈里澄清。

## 4 条目设计
以 `<desk>/references/review-cards.md`（含 "Low Reading Load" 一节）为准，这里只列访谈要额外注意的：
- **先定沙盘，再写卡片。** 讲结构的轮次——有哪些东西、谁产生、谁修改、谁能看到、怎么流动（角色、数据对象、端到端流程）——做沙盘：`OBJ` 写对象，`FLOWS` 写流程（或只写连线 `PANO_EDGES`），不用算坐标。首个项目 R01–R03 画的是平台里的对象和流程，R08 画的是"基线 → 派生契约 → 阶段"。spec 起草后，§5 角色、§6 数据对象、§9 状态就是沙盘的材料。只有几件小事、没有结构要画时写 `NO_SANDBOX`，一句话说明为什么。卡片上的图只画这张卡自己的那一块；一个沙盘视角能讲清一张卡的全部上下文时，卡片用 `view` 连过去。
- **一点一决定。** 一张卡可以有多个点，每个点只问一件事；顺带改正的内容单独成点，标"（顺带改正）"。
- **按信息形态选卡。** 一组相关的规则或推断 → 分组确认（`group`）；几种做法选一 → 多选一（`choice`）；可以选几个 → 可多选（`multi`）；只有用户知道的事实（人数、日期、名单）→ 填写（`fill`）；单条陈述 → 确认（`confirm`）。表格只放参考信息，不当决定的容器。
- **默认显示的一层要短，记录要全。** 需要细看的卡写简报四格（`brief`）：① 你在决定什么；② 我推荐 与 ③ 你会失去什么（并排、一样大，推荐不能不写代价）；⚖ 实话（推荐不是用户自己的优先顺序会选的、你最没把握、或某个前提能推翻推荐时必写，写得和正文一样直白）；④ 不同意会怎样。完整的理由、背景、证据照原样写在正文字段（`plain`、`context`、`evidence`……），页面收进折叠，一个字都不删。会改变决定的事实（前提、代价、门槛、依赖）必须在默认显示的一层。超出字数预算时拆卡，不删内容，也不把会改变决定的事实挪进折叠。
- **能画就画，两边都画。** 两个选项逐条比、什么情况下答案会变、一个数的分界线、步骤、谁先谁后、前后结构对照、数量，各有对应的图，由模板按数据画（`vis`，类型见 review-cards.md L3）。图要画出两边；数字旁边写清怎么数的、前提是什么。
- **选项两边都写。** 每个选项都写好处、代价、选了之后会怎样、选错了怎么退，不只写推荐的那个；会影响别的卡时写出来（`fx`）。
- **改动写成对照。** 改现有写法的分组卡（定稿修订、变更提议、按反馈修订）用对照式的点：位置、现在的写法 → 改成的写法；同意要放弃的写进"会失去"；不同意不等于保留原样时，写明不同意就怎样。点的完整说法仍写在 `title` 里（反馈 md 用它）。
- **每个点要有**：提议（只看标题就能做决定）、理由、风险（有就写）、不同意的话会怎样、抽象时给场景例子；原文与落点只在要批准的正是那段文字时给。
- **标来源与分量。** 来源：你已定（复述用户的决定）/ 推断（Claude 补的）/ 冷读（冷读发现）/ 建议（Claude 的提议）。分量：需要细看（改基线、范围、权限、数据外发、时间安排）/ 可快速确认。整张卡是 Claude 的提议时，`from` 里写"我的建议"（审批台据此归类）。
- **复述必须对照原话。** 凡是"你说过/你定了"的内容，发布前对照 log 里的用户原话和 decisions.md。
- **页面速览（`BRIEF`）**：你要定 / 我的结论 / 实话 / 前提，各一句；有一张卡最需要细看时加一行。cfg 的 `LEAD`（导语）照写，页面会把它收进折叠，所以导语里用户必须知道的事要写进速览。
- **上一轮怎么处理的（`PREV`）**：上一轮每条 → 用户的表态 → 怎么处理 → 写成了哪个编号 → 状态（这一轮还要定写 `open`，已结束写 `done`）。用户靠它确认自己的意见被正确理解。
- **议程进度（`AGENDA`）**：Q 编号、名称、状态（`now` 本轮 / `part` 本轮先定一部分 / `done` 已定 / 空 = 还没开始），让用户知道还剩多少。终止条件 T1–T7 在 `project.js` 的 `TCOND` 里，每轮都显示。
- **最后一条问下一步。** 签署轮问"本轮之后 spec 怎么处理"；阶段转换时问"下一步做什么"。
- **推荐不是默认。** 多选一要有推荐并写理由，但页面不预填任何答案。

## 5 与审批台的接口
构建目录是 `interview/reviews/build/`，里面只放这一轮的 cfg、数据和代号表；模板、导出模块和自检都取自 `<desk>`，不复制进项目。（项目要固定审批台的版本时，把开源仓库克隆到项目里并固定在一个提交上：`git clone https://github.com/xiuyu0000/interactive-approval-desk skills/interactive-approval-desk`，再 `git -C skills/interactive-approval-desk checkout <提交号>`；`<desk>` 就指这份副本，本 skill 的脚本先找它。）

1. **共用设置**（`init_interview.py` 已生成）：
   - `project.js`：每轮相同的数据——终止条件 `TCOND`（按 D-001 改写说明）、常用名词 `TERMS`、正文里会出现但代号表认不出的代号（T1–T7、AC1…）的解释。
   - `cfg_template.json`：`PROJECT`（项目标识，只用字母、数字、`_`、`-`，最长 24 个字符；本地打开的页面靠它区分项目的浏览器存储）、`REVIEW_DIR`（`interview/reviews`）、`REVIEW_PATH_HINT`、议程与终止条件两块的标题。
2. **每轮的 cfg**：复制 `cfg_template.json` 为 `cfg_rXX.json`，填 `ROUND`、`TOPIC`（本轮主题，用在文件名里，不能含 `/` `\`）、`TP`（发出轮次 Txx）、`TF`（预计的反馈轮次）、`LEAD`（导语），`data` 写 `["project.js", "data_rXX.js"]`。`TP`、`TF` 写进反馈 md 的轮次行，提案、反馈和对话轮次就连起来了。
3. **每轮的数据** `data_rXX.js`：`ROUND`、`TOPIC`（与 cfg 一致）、`ITEMS`；按需 `BRIEF`、`AGENDA`、`PREV`、`DELTAS`（本轮最关键的几件事）、沙盘（`OBJ` 加 `FLOWS` 或 `PANO_EDGES`）或 `NO_SANDBOX`、`TERMS_NOAUTO`（本页另有意思、不要自动加悬浮的词）。`project.js` 已经声明了 `TCOND` 和 `TERMS`：数据里要加名词写 `Object.assign(TERMS, {...})`，只在本页出现的代号写 `Object.assign(CODES, {...})`，不要再用 `const` 声明同名的量。字段的形状与上限见 `<desk>/round_template/README.md`，例子在 `<desk>/round_template/sample/`。
4. **代号表**：`python3 <skill>/scripts/desk_codes.py <项目>`——按权威顺序收集已有的 spec.md、派生契约、decisions.md、open_items.md、sources.md、INDEX.md、reviews/INDEX.md 和各轮反馈，调用 `<desk>/scripts/build_codes.py` 写出 `interview/reviews/build/codes.js`。本 skill 的编号都在审批台默认认得的形状里（D-001、FR-PLAN-01、R03-07、M5 这四类），不需要 `--shapes`。
5. **构建**：在 build 目录运行 `python3 <desk>/round_template/build.py cfg_rXX.json`，得到 `Rxx_<主题>_proposal.html`（本地完整版）和 `Rxx_<主题>_artifact.html`（发布用）。看它的提示：不认识的 cfg 字段、cfg 与数据的 `ROUND`/`TOPIC` 不一致。
6. **自检**：`NODE_PATH=<装有 playwright 的 node_modules> node <desk>/round_template/test.js Rxx`，结尾必须是 `✓ 全部通过`（代号、版面、字数预算、读得清、托管与本地导出、手机宽度……）。没通过不发布；未解释的代号补进 `CODES`，不要为了躲检查改写正文。
7. **审批者冷读（两遍）**：`NODE_PATH=… node <desk>/round_template/dumptext.js out.txt Rxx`，把材料交给一个没读过任何记录的子 Agent，扮演忙碌的审批者。第一遍只读默认显示的内容，逐卡说出：在定什么、我推荐什么、要失去什么、不同意会怎样、它自己会怎么答、有几分把握。第二遍读全部展开的内容：答案或把握变了，就把让它变的事实挪到默认显示的一层。也问它哪里看不懂、缺什么（例子、后果、风险）、哪里多余或分组不当，沙盘有没有讲清卡片依赖的结构（不做沙盘的，理由站不站得住）。改到没有卡挡住决定、第二遍不再改变答案为止。
8. **发布**：用 Artifact 工具发布 `Rxx_<主题>_artifact.html`，声明 `capabilities: {db: {}, downloads: true}`；发布后列一次数据库的 `feedback` 集合，确认能用；把 Artifact 卡片给用户。本地副本放 `interview/reviews/Rxx_<主题>_proposal.html`（已有同名文件时先备份成 `.backup.html`），发布版放 `interview/reviews/artifact/`，链接与审批台版本登记进 `reviews/INDEX.md`。用户审批中途的进度在数据库的 `drafts/Rxx`。
9. **不能变的键**：浏览器存储键 `{PROJECT}/Rxx-feedback-v1`（发布后条目含义变了，把数据里的 `KEY` 改成 `Rxx-feedback-v2`，旧答案和旧草稿都不再套用）、数据库的 `feedback/Rxx` 与 `drafts/Rxx`、反馈文件名 `Rxx_<主题>_feedback.md`。

不能发布 Artifact 的环境，用本地文件：在 Chrome 或 Edge 里打开本地副本，页面把 md 写进选定的 `interview/reviews/`，否则下载一份。

## 6 处理反馈
**取回**（用户说"反馈完成"后）：
1. 读该轮 Artifact 数据库 `feedback/Rxx` 的 md 字段。
2. 同时看另外两种来源。一是用户贴在对话里的 Markdown：页面提交失败时（网络断断续续也会，v3.7.1 只马上重试一次）说"没有提交成功"，选中下方的 Markdown，请审批者复制发过来。二是用户另存的 `Rxx_<主题>_feedback*.md`：页面上的"💾 另存一份 md 到本机"（发布时声明了 `downloads`），或本地打开的页面写进选定文件夹、下载的文件，多在 `interview/reviews/` 或"下载"文件夹。所以数据库里可能什么都没有，也可能是更早的一次提交。"下载"文件夹要用户授权才能看；没有授权时，请用户把文件放进 `interview/reviews/`。
3. 比较每份的"- 导出时间："一行，把最新的一份原样写成 `interview/reviews/Rxx_<主题>_feedback.md`；那里已有更新的文件时不覆盖。在 `reviews/INDEX.md` 写明用的是哪一份（数据库 / 对话里贴的 / 另存的文件），并告诉用户。
4. 都没有：数据库 `drafts/Rxx` 里是用户的进度和半成品 md，只能用来看进度，不能当反馈（实在要用，先跟用户说清楚）；请用户回到页面再点一次"提交反馈"，或复制 Markdown 发过来、另存一份。

反馈文件每条有：状态（✅ 通过 / 🤔 待微调 / ❌ 需修改 / 未表态）、所选选项、分组卡的逐点表态（同意 / 要调整 / 不同意，各带说明）、填写的内容、评论。用了简报、图、对象写法选项的卡，md 里还有简报、图的文字版、选项的好处与代价等几行：那是提案内容，不是用户的回答。处理规则：

| 反馈 | 处理 |
|---|---|
| 通过（含所选选项） | 记 D：写批准的内容本身（不写"同意 R01-05"），来源写"Rxx-nn / Txx" |
| 通过，评论有补充 | D 写入补充；评论里的事实另记 F |
| 待微调，评论给出明确改法 | 按评论写 D，注明"按评论调整" |
| 待微调，需要细化 | D 状态写"有效（细节待 Rxx-nn）"，下一轮给细化方案 |
| 需修改 | 不记 D，下一轮重新提案；用户说明是误解的，按澄清后的意思重写 |
| 只写评论、没选选项 | 以评论为准记 D，注明"未选选项，以评论为准"（首个项目 R08-05 → D-094） |
| 勾选与评论对不上 | 记 Q（澄清），下一轮问（R01-04：只勾了 M1/M2/M5，却对 M3 写了评论） |
| 评论与已批准决定冲突 | 记 Q（冲突），下一轮由用户拍板，不自行调和（R01-04 的评论"Agent 审核证据"与 D-009"Agent 只提示"） |
| 填写项没填 | Q 状态不变，下一轮用填写卡再问；到交接时仍未答，列入待决并写清谁、何时补（R07-04 → Q-34） |
| 评论带出新能力或新范围 | 下一轮作为提议，不自行加入 |
| 用户把判断交给 Claude | 记 D（授权范围与判断标准）；判断时给出理由，按约定展示（D-065） |
| 分组卡逐点表态 | 同意的点记 D；要调整、不同意的点按上面的规则；没表态完的组（"未完成（已表态 x/n）"）当未答处理 |
| 批量表态 | "本组批量同意""全页一键通过"（包括"全页一键通过时按推荐方案填入"的选项）照样是用户的表态，记 D 时在来源里注明；逐点表态（`bulk: false`）的组不会被一键填上 |

新决定写入后，检查它是否让某条假设（A）或旧决定不再成立；旧决定被取代的，在 decisions.md 标注。

处理完，在 log/Txx.md 写"反馈要点"和"Claude 的处理"两节（照首个项目 T04–T16 的格式）。

## 7 澄清轮
用户粘贴某条内容或链接问"这是什么意思"：
1. 先回答：为什么有这条、具体怎么判断、场景与例子（虚构但贴近项目）、它意味着什么、有什么盲区。
2. 告诉用户：觉得过严或过松，可以在该条评论里提出。
3. 发现是自己写错了：直接承认，改措辞；用户补充的事实记 F；带出的新问题记 Q 并在本轮新增条目；重建、自检后在原链接重新发布（本地副本先备份；已填的答案按条目编号保留；条目含义变了，把数据里的 `KEY` 升到 `Rxx-feedback-v2`）；`TF` 与反馈轮次顺延。
4. log 写"本轮决定：无（澄清）"，或列出新增的 F、Q。
