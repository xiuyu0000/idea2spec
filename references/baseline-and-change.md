# 签署、定稿、版本、变更、派生契约、交接

## 1 签署轮（首个项目 R04）
spec v0.x 经过冷读后，用一轮审批台请用户签署：
- 契约管哪个阶段（例：只约束第一版灰度测试，正式阶段的差异作为后续变更）；
- 起草与冷读中发现的冲突（每个冲突单独一卡，给选项）；
- Claude 补的推断，按主题分组确认；
- 怎样才算验收通过（阶段门槛）；
- 冷读结果摘要；
- 最后一条"本轮之后 spec 怎么处理"（多选一，每个选项写好处、代价和选了之后会怎样）：A 按本轮结论修订、冷读，通过后批准为基线 v1.0（推荐）；B 修订后再给我看一次全文；……

## 2 要不要再开一轮
签署轮之后按反馈修订、冷读，再决定定稿还是再确认一轮。用户可能把这个判断交给 Claude（首个项目 D-065）。标准：
- **再开一轮（只核对、不重谈）**：有按用户简短评论展开的新流程，其中细节是推断；或冷读发现权限空缺、验收条件因此改变。
- **直接定稿**：其余改动都是由已批准决定推出的一致性修订——展示修改处（diff 文件 + 审批台上的修改总览）、说明理由后定稿。

首个项目：R05（9 条）→ R06（5 条，只核对）→ 定稿。

## 3 定稿步骤
1. 写入最后一轮结论；去掉 `[推断]` 与"待确认"（获批的推断改为引用对应的 D 编号）。
2. 最后一次冷读（两个视角；必要时定向核对）。
3. 自检：`templates/selfcheck.md`（T1–T7 逐条 + 契约定义第七节 7 问），写 `research/selfcheck.md`。
4. `check_spec.py --baseline` 无错误。
5. 头部状态改为"已批准基线 v1.0（日期，D-xxx）"；decisions.md 记批准；INDEX.md 当前状态更新。
6. `snapshot_spec.py --version v1.0` 存快照与逐行对比。
7. 定稿修订（不改目标、范围、权限，由已批准决定推出）不单独开轮，但在下一轮审批台逐组列出交用户核对（对照式的点：位置、现在的写法 → 改后的写法；首个项目 R07-01：16 组 34 处）。

## 4 版本
- v0.1 起草；每次按冷读或反馈修订升 v0.x；用户批准为基线 → v1.0；每并入一个变更 → v1.x。
- 每次升版本：快照 `interview/spec_versions/spec_vX.Y.md` + 逐行对比 `diff_vA_vB.md`（`scripts/snapshot_spec.py`）；头部"修订记录"加一句。
- 文中修订标注保留（"（第 N 轮冷读修订）""（v1.0 定稿修订）""（CR-xxx）"），读者能看出哪里改过。

## 5 变更（基线之后）
- 任何新增、修改、取消，都写成 CR 提议（`templates/CR_proposal.md`）：编号、位置、现在的写法、提议的写法、理由、验收条件变化。
- 由用户在审批台批准（可以和当轮其他条目一起）：用对照式的点，每处写位置、现在的写法 → 提议的写法，代价写进"会失去"，验收条件的变化写在点上。
- 并入：正文改写并标"（CR-xxx）"；§14.1 加一行（内容、原因、影响的需求、验收条件变化、提出人、批准人、日期）；§14.2 保留修改前原文；被取代的决定在 decisions.md 标注；§11 的假设、§13 的待决随之更新；升 v1.x；快照与对比；CR 文件 status 改为"已批准，并入 vX.Y"并写批准结果。
- 设计或实现中遇到需求做不到、有歧义或互相冲突：停下，记下影响的需求编号，交需求方决定；不得自行放宽需求或验收条件。

## 6 派生契约（按需）
用户要分阶段交付（如 2–3 天的交互原型、一周的 MVP、按周迭代）时，基线描述的是目标状态，阶段安排另立派生契约（首个项目 D-069 起）。
- **能做**：裁剪基线范围；补充本阶段的要求（演示内容、访谈规程、关口、节奏）；写明经需求方批准的**限时过渡做法**（注明依据与恢复基线写法的时点）。
- **不能做**：改变基线的需求内容。要改，按基线 §14 提变更。冲突时以基线为准。
- **流程**：方案审批（阶段、角色、范围、关口、节奏）→ 起草 → `check_spec.py <项目> --file <派生契约>.md` → 冷读（读基线与派生契约）→ 签署 → `snapshot_spec.py --file <派生契约>.md --version v1.0`。
- **MVP 草稿对照**：MVP 契约可以先作草稿。原型评审后只有小改动（不改基线需求）→ 修订为正式版签署；有大改动或要重做原型 → 先批准基线变更、再改原型、再评审，循环到收敛（首个项目 D-088）。
- **结构参考**（实物见本机范例项目，位置写在 `local.md`）：交互原型契约——与基线的关系、目的与成功标准、要回答的问题、不做的事、阶段工期与角色、开工关口、演示场景、演示数据与故事线、访谈规程、产出与评审关口、研发要求、验收、待决、变更、追溯；MVP 契约——范围（纳入/简化/推后/限时过渡）、阶段要求、验收用例、适用的不变量、上线要求、每周增量、角色、关口与变更、反馈、指标门槛、实现基线的条件。
- 首个项目参考了用户的《双 Agent 研发管理方案》（阶段 S0 准备、S1 原型、S2 MVP、S3 每周增量、S4 收口；关口 G0/GP/GM/GW/Gv1；证据等级；变更三级）。本 skill 对应 S0 之前的"需求梳理"阶段（首个项目 D-072，目标 2–3 天）。

## 7 交接
需求梳理结束时写 HANDOFF.md（`templates/HANDOFF.md`）：
- 文件与阅读顺序（谁读什么、状态、怎么用）；权威顺序。
- 开工前检查（关口、通过标准、当前状态）与要提前发起的外部申请。
- 两个 Agent 的规则文件要点：实现 Agent（CLAUDE.md）与审查/验收 Agent（AGENTS.md，可以是另一家厂商）——契约路径与权威顺序、不变量清单、遇到冲突停下交需求方、变更分级、测试命令；实现侧"先出计划，批准后改代码"；验收侧"黑盒验收不看实现代码，只按契约操作运行中的软件"。
- 阶段产出与关口要查的东西。
- 未定事项：编号、事项、谁定、什么时候。
- 什么时候回来找 Claude（如原型评审后签正式 MVP 契约、需要改基线时）。

同时更新 INDEX.md 的当前状态，以及 claude.ai Project 里的指针文档（如有）。
