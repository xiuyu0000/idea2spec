# 冷读

## 规则
- 冷读读者是**独立的子 Agent**，只读契约文件（spec.md，以及派生契约），**不读 interview/ 下的任何记录**。实现者和验收者手里也只有契约；读者若看了访谈记录，会用背景知识补上文档的空白，问题就查不出来。
- 每轮同时启动两个视角：设计者、验收者（两个独立子 Agent，并行）。修订后可以只做"定向复核"（只读改动处与相关条文）。
- 退出条件（终止条件 T7）：设计者"阻塞：无"；验收者提出的不可判定项与矛盾全部改写。之后再发现的歧义按 §14 变更处理。
- 首个项目：v0.1 → v1.0 共六轮加一次定向核对，设计者的阻塞问题依次为 8、9、7、7、3、0；派生契约与 v1.1 又做了第七轮加一次定向复核。留出 3–6 轮的时间是正常的。
- 审批台发布前的审批者冷读（两遍：先只读默认显示的内容，再读全部展开的）是另一回事，见 `interview-rounds.md` 第 5 节第 7 步和审批台的 `references/review-cards.md` 第 6 点。

## 提示词：设计者视角
（给 Agent 工具的 prompt；填入文件的绝对路径）

```
你是一位没参加过需求讨论的设计者兼实现者，要只凭下面这份需求契约开始做系统设计。
只读这些文件：<spec.md 路径>[、<派生契约路径>]。不要读其他任何文件，也不要搜索项目里的其他内容。

请找出：
1. 阻塞问题：不问需求方就无法设计的地方（缺对象、缺规则、权限或流程有空缺、两处规定互相矛盾而无法同时满足）。每条写：位置（章节或编号）、问题、为什么阻塞、需要需求方回答什么。
2. 非阻塞问题：能设计，但不同实现者可能做出不同结果的地方。
3. 内部矛盾：两处规定不一致的地方，引用两处原文。

不要提设计方案，不要评价需求好坏。最后一行写"阻塞：N 处"（没有就写"阻塞：无"）。
```

## 提示词：验收者视角

```
你是独立验收者，没参加过需求讨论，要只凭下面这份需求契约判断交付是否通过。
只读这些文件：<spec.md 路径>[、<派生契约路径>]。不要读其他任何文件，也不要搜索项目里的其他内容。

逐条检查每个验收用例（ACn）、每条不变量（INV）、每个指标和阶段门槛：
1. 不可判定：只凭文档无法判断通过与否的（缺构造方法、缺期望结果、口径有多种读法、边界没说、证据要求不明）。每条写位置、为什么不可判定、建议改成什么。
2. 矛盾：文档内互相冲突的规定。
3. 缺失：有规定但没有对应验收用例的（尤其是不变量与禁止行为）。

最后一行写"不可判定 N 处、矛盾 N 处、缺失 N 处"。
```

## 提示词：定向复核

```
下面这份需求契约刚按上一轮冷读意见修订过，修订处在文中以"<标注，如（第 3 轮冷读修订）>"标出。
只读：<文件路径>。不要读其他任何文件。

只检查修订处及其直接相关的条文：修订是否解决了问题，是否引入了新的阻塞、不可判定或矛盾。
最后一行写"阻塞：N 处；不可判定 N 处；矛盾 N 处"。
```

## 怎么处理发现
| 发现 | 处理 |
|---|---|
| 能由已批准决定直接推出的澄清（技术性、一致性） | 直接改，标"（第 N 轮冷读修订）"；定稿后在下一轮审批台逐组列出交用户核对 |
| 影响范围、权限、可见范围、验收标准、数据外发的 | 记 Q（类型"冷读发现"），放进下一轮审批台由用户拍板；决定前在 spec 写明暂行写法 |
| 要补一条规则才能闭合，但没有决定可依 | 写成 `[推断]`，交用户确认 |
| 基线批准后才发现的问题 | 整理成 CR 提议，走变更 |

## 记录
写 `interview/research/coldread.md`（`templates/coldread.md`）：每轮写读了哪个版本、两个视角的发现（按类计数并概括）、怎么处理、版本升到多少。最后写结论：按 T7 是否满足。
