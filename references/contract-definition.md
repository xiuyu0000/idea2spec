请为当前项目撰写一份“需求契约文档”。

我所说的需求契约，是供需求方、设计者、实现 Agent 和独立验收者共同遵守的项目级需求基线。

请把已有研究、真实问题、用户目标与有效决策，转译为边界明确、责任明确、行为明确、可独立验证的系统承诺。文档应使没有参与此前讨论的人，能够理解：

为什么做、为谁做、要达到什么状态、明确不做什么；
各主体在什么条件下承担什么责任、拥有什么权限；
哪些规则在整个过程中都不能破坏；
正常、异常和缺少证据时，系统分别应该怎样表现；
凭什么认定完成，以及需求应当如何变更。

这份文档的价值，在于减少后续设计、实施和验收时对我个人解释与临场判断的依赖。

一、先理解资料和需求本质

先阅读当前项目已有的研究、需求、决策记录及相关约束，识别：
- 真正要解决的问题、发生场景及其代价；
- 用户希望得到的结果；
- 已确认的原则、取舍、边界和授权范围；
- 尚未解决的矛盾、假设与待决事项。

区分来源事实、已批准决定、你的推断与建议。
已有实现可以帮助核验现状，但不能直接反推为用户需求。
发现资料冲突时，结合项目权威链和后续有效决策说明冲突及影响，不自行改写上游约定，也不覆盖历史。

优先利用已有资料解决问题。只有会实质改变目标、范围、权限或验收条件的缺口，才需要向我澄清；其余可以标明假设或待决状态，继续完成不受影响的内容。

二、把目标写成可以履约的承诺

清楚说明系统直接负责什么，以及哪些结果只能由系统支持、最终依赖用户或外部条件。

对关键需求，按实际需要写清：
- 适用场景、触发条件和前置条件；
- 责任主体及必要输入；
- 系统应产生的可观察行为、输出或状态变化；
- 权限、禁止行为和不可破坏的约束；
- 失败、冲突、缺输入或缺证据时的处理；
- 验收条件、验证方式和所需证据；
- 对应的上游依据。

为需求设置稳定编号，使目标、需求、约束、验收与来源能够互相追溯。
避免只写“支持某功能”“智能处理”“优化体验”“基本完成”等无法据此判定履约的描述。

三、覆盖完整行为与责任

根据项目实际，覆盖：
- 背景、问题、用户、目标和成功标准；
- 本次范围、可选范围及明确不做的事项；
- 关键术语、场景和端到端流程；
- 角色职责、决策权、执行权及交接关系；
- 功能行为、生命周期和状态转换条件；
- 系统不变量及不得恶化的条件；
- 输入输出、数据含义、生产者、消费者和修改权限；
- 异常、未知状态、降级、恢复和停止条件；
- 可靠性、隐私、成本、维护负担等适用要求；
- 验收标准、阶段门槛、依赖与证据要求；
- 来源、未决问题、版本状态和变更规则。

结构和篇幅服从项目需要，不为填满模板增加无意义的章节。
不要自行新增没有需求依据的功能、岗位、指标、审批或流程。

四、把验收写到能独立判断

验收条件应让独立验收者依据文档及其引用，判断通过或不通过。

按需求性质选择自动测试、人工审阅、真实集成、连续运行或用户确认等验证方式，并说明必要的环境、周期、判定者和证据。

明确区分：
需求已获准；
能力已实现；
静态或隔离测试已通过；
真实运行或效果验收已通过。

不得以文档、配置、演练、任务勾选或执行者自述，替代契约要求的实际证据。缺证据应明确记录，不能通过推断补成成功。
指标如涉及计算，应交代口径、时间范围、有效输入和缺失值处理。

五、保持需求、设计和任务的分工

需求契约主要规定“为什么做、系统应怎样表现、受到哪些约束、怎样才算通过”。

保留项目已经明确批准的技术、环境、接口和数据约束，并注明依据。
尚未决定的技术选型、内部算法和实现结构交给设计文档；施工顺序和工作分解交给任务文档。

项目级需求契约与单项任务契约应分别处理，不机械套用同一组字段、数量限制或预算规则。

六、准确处理授权和变更

标明文档是待确认草案还是已经获准的基线，不虚构批准。
已有授权应按其实际范围使用，不机械重复询问，也不扩大解释。

如果已有需求基线，明确指出本次新增、修改或取消了什么，以及原因和影响；遵守项目既有变更流程。
下游设计或实现遇到困难时，应暴露问题，不能通过偷偷放宽需求或验收标准来获得通过。

七、交付前自检

请检查：
- 每项关键需求是否服务于明确的问题或目标？
- 不同 Agent 是否可能对同一句话产生影响交付的不同解释？
- 正常路径、失败路径、权限和交接责任是否完整？
- 有没有把假设、建议或代码现状写成已确认需求？
- 有没有承诺系统无法控制的结果？
- 验收证据是否足以证明相应承诺？
- 未参与讨论的实现者能否据此开展设计，独立验收者能否据此作出判断？

请直接交付完整的需求契约草案，并附必要的来源与待决事项。
