# 首个项目的教训

每条：现象（出处）→ 规则。第 1–21 条的出处指首个项目 `interview/` 下的记录（本机位置见 `local.md`）；第 22 条起是审批台后来的版本带来的规则。以后的项目有新教训，按同样格式追加。

## 开局
1. **附件没到就起草，全部返工**（T01→T02）：契约定义没上传成功，暂定终止条件 A–D 在 T02 被全部取代。→ 先确认契约定义和用户提到的附件都读到了；没读到直说。
2. **通用规格清单与契约定义冲突**（T02）：借用的"开放问题不超过 3 个""拆里程碑、选技术"与定义第五节冲突。→ 终止条件从契约定义推导，不套用数量限制，不写设计与任务。

## 访谈
3. **复述用户的事实写错了**（T12、T13）：把"人上传纪要、Agent 起草共识与待办"写成"会议纪要起草"；举例时说设计稿没有项目归属，用户指出设计工作归属产品项目、与开发在同一项目内。→ 发布前，把条目里所有"你说过/你定了"的内容对照 log 原话与 decisions.md。
4. **评论与已批准决定冲突**（T04）：R01-04 的评论"Agent 审核证据"与刚批准的"Agent 只提示，不下结论"（D-009）可能冲突。→ 记 Q（冲突），下一轮问；不自己调和。
5. **勾选与评论对不上**（T04）：只勾了 M1/M2/M5，却对 M3 写了评论。→ 下一轮澄清。
6. **只写评论，没选选项**（T16）：R08-05 没选任何选项，评论给出了选项之外的第四种处理。→ 以评论为准记 D，注明"未选选项，以评论为准"，相关假设一并改写。
7. **同一个词，用户和你理解不同**（T05→T06）：R03-07"各项目花的时间"，用户指平台使用耗时，Claude 理解成员工在各项目上的工作时间。→ 关键名词第一次出现时用例子复述含义。
8. **动词没有承接对象**（T05）：多处写了"提醒"，却没定义提醒发到哪里，第三轮才补上收件箱。→ 每个提醒、通知、同步写清渠道、接收人、处理后的状态。
9. **外部最佳实践被用户否决**（T08）：推荐"时长只看 ≥5 人汇总"，用户改为按个人统计、只对开发者可见（D-049）。→ 调研结论只当推荐与启示；用户的决定才是需求。
10. **"默认可行"的外部条件**（T01、D-013）：用户说软件文档接入"默认认为可行"。→ 记外部依赖假设 A-xx，spec 写不成立时的降级行为。
11. **填写项没人填**（R07-04 → Q-34）：试点人数、开工日期、关键人员的时间没填。→ 保留为 Q，下一轮用填写卡再问；交接时仍未答就列入待决，写清谁、何时补。

## 起草与冷读
12. **冷读一轮查出很多问题是常态**（coldread 第 1–6 轮）：设计者阻塞问题依次为 8、9、7、7、3、0。→ 留出 3–6 轮冷读的时间；每轮按"直接改 / 交用户 / 标推断"分流。
13. **基线之后的决定无处安放**（CR-002 ①②）：原规则"晚于基线的决定都要先并入基线才生效"，让原型、MVP 这些研发安排失去依据；MVP 第 1 周的临时做法被冷读判为越界。→ §0.5 一开始就写清：只涉及研发过程或派生契约的决定直接生效；派生契约可写经批准的限时过渡做法。
14. **新决定让旧假设守不住**（CR-002 ⑨）：逐字稿必传后，"参与者不输入保密信息"的假设守不住。→ 每次新决定写入后，检查 §11 的假设是否仍成立。
15. **spec 里的待决没登记**：spec §13 的 Q-20、Q-22 没有登记进 open_items.md；早先决定的状态（如"部分有效"）在后续轮次定下细节后没有回头更新。→ 进 spec 的 Q、A 也登记；状态随后续决定更新；`check_spec.py` 与 `status.py` 会提示。

## 审批台（这些规则已内置于审批台 skill）
16. **代号没有解释**（T07 → v3.2）：用户看不懂 M5、M6 指什么。→ 页面上每个代号都带悬浮解释，未定义代号为 0 才能发布。
17. **表格捆绑多个决定**（T15 → v3.3）："编号 / 内容 / 是否推断"表格认知负担大、表头意义不明、上下文不全。→ 按主题分组的决定卡，一点一决定，给全背景。
18. **默认同意分不清**（T17 → v3.4）：中断后回来，分不清哪个"同意"是自己点的。→ 不预填任何答案，批量同意要显式点击并标出。
19. **说明长得都一样，抓不住注意力**（T17 → v3.4）：场景、理由、要注意、不同意的话折叠起来，各有样式。
20. **发布后改了条目**（T12、T15）：已填答案按条目编号保存，含义变了要换本地存储键，否则旧答案会套到新问题上；反馈轮次顺延要记下。

→ 用户对审批台的意见，改审批台 skill 本身（在它的开源仓库里改，见 interview-rounds.md 第 8 节），保持最新版。

## 其他
21. **没有删除权限**（T13）：误建的重复文件删不掉。→ 移到 interview/_to_delete/，在 INDEX.md 说明，请用户删。

## 审批台后来的版本（出自后续项目；第 22–24 条的细节见审批台 CHANGELOG.md 里对应的版本）
22. **不同项目的本地页面串了答案**（v3.6）：本地打开的页面共用一份浏览器存储，另一个项目的同号轮次读到了这边的答案，没碰过的卡显示为已通过并进了导出。→ cfg 必须写 `PROJECT`（init_interview.py 已填）。
23. **卡片字太多**（v3.7）：一张卡在选项前显示约 3,900 字，审批者说阅读负担和审批压力太大。→ 简报四格、按数据画的图、折叠；自检按字数预算卡住长卡，放不下就拆卡，不删内容。
24. **讲结构的轮次没有沙盘**（v3.7.1）：两轮讲角色、交接和流程的审批台都没做沙盘，每张卡各画一块，审批者问是不是不要沙盘了。→ 写卡片前先定沙盘；不做就写 `NO_SANDBOX` 说明为什么。
25. **网络不稳，反馈没进数据库**（用 v3.7.1 时）：审批者答完点提交时网络断断续续，草稿和反馈一笔都没写进数据库（v3.7.1 的提交只马上重试一次），页面说"没有提交成功"，审批者用"💾 另存一份 md 到本机"存下了文件。→ "反馈完成"时同时看数据库、对话里贴的 Markdown 和另存的 md，比较导出时间用最新的一份，并说明用的是哪份；不要一上来就请用户重填。
