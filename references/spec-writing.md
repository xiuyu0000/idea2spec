# 怎么写 spec.md

契约定义（`contract-definition.md`）是上游；这里是首个项目里证明可行的写法。骨架见 `templates/spec_skeleton.md`；本机有范例项目时（见 `local.md`），实物在它的 `spec.md`。

## 1 每条关键需求要写清
| 要素 | 写什么 |
|---|---|
| 触发 / 前置 | 什么情况下适用 |
| 负责人与输入 | 谁做、必须提供什么 |
| 行为 | 系统可观察的行为、输出或状态变化 |
| 禁止 | 权限边界、不可破坏的约束（引用 INV） |
| 异常 | 失败、冲突、缺输入、缺证据、外部不可用时怎样 |
| 验收 | `ACn（方式）`：可判定的检查——怎么构造、期望看到什么 |
| 依据 | D/F/S/A 编号 |

按实际需要写，不为填满而写；但每条功能需求至少有一个验收用例和依据。

## 2 格式约定（check_spec.py 依赖这些约定）
- 功能需求标题：`**FR-<域>-nn 标题**`，放在行首。可以单独一行、下接 `- 触发：` `- 行为：` 等列表，也可以同一行接冒号写成段落。域只用大写英文字母（FR-PLAN、FR-MEET），序号两位（01–99）。
- 验收用例：`ACn（方式）：…`，方式取 AT 自动测试 / INT 真实集成 / MR 人工审阅 / PILOT 试点运行。§8 开头写一句缩写说明。
- 依据：`依据：D-005、D-018。`
- 不变量：§7 表格 `| INV-nn | 规则 | 依据 | 验收用例 |`，验收用例列写 `FR-PLAN-02 AC1、FR-PLAN-04 AC1`，每条不变量至少一个，引用的 FR 与 AC 必须存在。
- 修订标注：起草阶段未获批准的补充规则 `[推断]`；冷读修订 `（第 N 轮冷读修订）`；定稿修订 `（v1.0 定稿修订）`；变更 `（CR-xxx）`。说明这些标注本身时用反引号括起来（check_spec.py 不计反引号里的内容）。
- 编号一经发出不改号、不复用。
- 编号形状沿用 D-001、F-001、Q-01、A-01、S-01、CR-001、INV-01、NFR-01、FR-PLAN-01、M1、G1、N1、AC1：它们都在审批台默认认得的代号形状里（大写字母 1–3 个、短横、2–3 位数字，如 D-001；`FR-域-两位数`；`R03-07`；大写字母 1–2 个直接跟 1–2 位数字，如 M5、T04、AC1），审批台页面上能自动带悬浮解释。另起别的形状时，审批台要用 `build_codes.py --shapes`（check_spec.py 会提示不合形状的功能需求编号）。

## 3 各节要点
- **头部表格**：版本、状态（待确认草案 / 已批准基线 + 批准依据）、日期、需求方、依据（interview/ 的轮次范围、契约定义）、适用阶段、修订记录（每版一句）。
- **§0 如何阅读**：用途（只规定为什么做、系统怎样表现、约束、怎样算通过；设计与任务另有文档；写明"由设计提出、需求方批准"的事项须书面同意）；来源标记表；用语（必须/应/可；本项目特有的判定用语，如"逐字找到"怎么判）；时间规则（时区、工作日、到期怎么算、工期是否冻结、工作小时）——凡涉及时限都要写；**权威顺序**：契约定义 > 本文 > 派生契约 > 设计 > 任务卡，并一开始就写清 ① 基线之后的决定，只涉及研发过程或派生契约的直接生效，改需求内容的必须按 §14 并入；② 派生契约只能裁剪范围、补充阶段要求、写明经批准的限时过渡做法（注明依据与恢复时点）。
- **§1 背景、问题与代价**：来自 F 编号的现状与真实案例；"问题 → 应对"对照表，让每条需求都能追到一个问题。
- **§2 用户、目标与成功标准**：服务对象；目标 G1..；**系统直接负责 vs 只能支持**（方向是否偏离、风险是否成立这类结论由人判断）；指标表——编号、指标、客观口径（分子、分母、统计期、计入与剔除、边界、缺失时显示"无数据"而不是 0%、何时定稿不再重算）、主观修正、依据；用户定了"不用于评价个人"就写明。
- **§3 范围**：本次范围；后续阶段；明确不做（N1..，含依据）；与现有工具的关系。
- **§4 术语**：每个可能被不同 Agent 理解成不同东西的词。
- **§5 角色与权限**：角色表（谁、职责、依据）；验收/审批/裁定对照表（含上一级、回避、缺位）；权限矩阵（✔/✘/—）；可见范围表。
- **§6 核心数据对象**：对象、含义、生产者、修改者与修改规则。
- **§7 系统不变量**：任何功能、配置、设计都不能破坏的规则；每条有依据与验收用例。
- **§8 功能需求**：按域分组；开头写验收方式缩写。
- **§9 状态与生命周期**：每类对象的状态与转换条件、谁触发。
- **§10 非功能要求与约束**：只写已批准的（部署、规模、浏览器等）并注明依据；未约定的写进 §13，"由设计提出、需求方批准"。
- **§11 外部依赖与假设**：A-xx、不成立时系统怎样表现、依据。
- **§12 验收**：四种状态——已获准（基线版本号）/ 已实现（提交号与需求编号）/ 隔离测试通过（测试报告或审阅记录）/ 真实运行通过（运行记录、截图、导出数据、签字）；文档、配置、演练、勾选、自述不能代替证据，缺证据停在上一档并记缺什么；判定人（独立验收者 = 未参与该需求实现的人或 Agent）；阶段门槛（可判定的数字、周期、规模）。
- **§13 待决事项**：编号、事项、当前写法、影响、决定人与时机。
- **§14 版本与变更规则**：当前状态；变更必须写编号、内容、原因、影响的需求、验收条件是否变化、提出人、批准人、日期；设计或实现遇到困难时作为问题提出，不得放宽需求或验收条件；不改写历史。§14.1 变更记录；§14.2 修改前原文。
- **§15 追溯**：需求 → 依据。
- **附录**：算法、预测、重排之类的规则给固定样例（输入 → 期望输出），让验收可判。

## 4 消灭歧义（首个项目冷读里反复出现的问题）
- 每个"提醒/通知/同步/推送"写清发到哪里、谁收、处理后状态怎么变。
- "主管""负责人""相关人"这类称呼，在 §4 或 §5 定义唯一含义。
- 每个状态写清从哪些状态来、到哪些状态去、谁能触发；叠加状态（如逾期且待验收）写清怎么处理。
- 每个时限写清起算点、单位（工作日/自然日/工作小时）、到点时刻、非工作日怎么算。
- 每个指标写清分子分母、边界、缺失值、定稿时点。
- 每条"Agent 做什么"写清它只给意见还是能改状态；引文类输出写清怎么核对引文真实存在。
- 数据保存写清起算点，以及一份数据归属多个对象时怎么算。
- 可见范围写清"谁能看哪一部分"，包括派生出来的数据（如待办的出处原话）。
- 避免无法判定的词：智能处理、优化体验、及时、合理、尽量、适当、基本完成——要么删掉，要么给出判定方法。

## 5 不写什么
- 未决的技术选型、内部算法、实现结构（交给设计）；施工顺序、任务分解（交给任务文档）。
- 没有依据的功能、岗位、指标、审批、流程。
- 系统控制不了的结果（写成"支持，由人决定"）。
- 用户没批准的推断（起草阶段标 `[推断]` 交审批；基线里不能有）。
- 从现有代码或现状反推出来的"需求"。

## 6 交给冷读之前
1. `python3 <skill>/scripts/check_spec.py <项目>`，错误清零，警告逐条看过。
2. 自己按第 4 节过一遍。
3. 头部的版本、状态、修订记录已更新。
