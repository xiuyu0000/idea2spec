## 0. 如何阅读本文档

### 0.1 用途
本文档是需求方、设计者、实现 Agent 与独立验收者共同遵守的项目级需求基线。它规定**为什么做、系统应怎样表现、受哪些约束、怎样才算通过**。技术选型、内部算法与实现结构由设计文档决定；施工顺序与工作分解由任务文档决定（D-002）。凡写明"由设计提出、需求方批准"的事项，设计文档必须给出方案并取得需求方书面同意后才能实现。

### 0.2 来源标记
| 标记 | 含义 | 出处 |
|---|---|---|
| `D-xxx` | 需求方已批准的决定 | `interview/registry/decisions.md` |
| `F-xxx` | 需求方陈述的来源事实 | 同上，"来源事实"一节 |
| `S-xx` | 外部调研来源 | `interview/registry/sources.md` |
| `A-xx` | 假设（含外部依赖） | 本文 §11 |
| `Q-xx` | 待决事项 | 本文 §13 |
| `[推断]` | 起草阶段标记未获批准的规则；基线中不得出现 | — |

### 0.3 用语
- "必须"：不满足即不通过验收。"应"：默认要求，偏离需在设计文档说明理由并经需求方同意。"可"：允许但不要求。
- <本项目特有的判定用语及其判定方法>

### 0.4 时间规则
<涉及时限时写：时区；工作日与节假日表由谁维护；"N 个工作日后到期"怎么算（含例子）；非工作日发生的事件从何时起算；工期是否冻结；工作小时。不涉及时限就删除本节。>

### 0.5 冲突时的权威顺序
1. 需求契约概念说明（方法）。
2. 本文是唯一的需求基线。基线批准后，`decisions.md` 中的新决定：只涉及派生契约或研发过程的，直接约束派生契约或研发过程；要改变本文需求内容的，必须按 §14 并入本文后才生效。
3. 派生契约（如交互原型契约、MVP 契约）只能裁剪本文的范围、补充阶段性要求，或写明经需求方批准的限时过渡做法（须注明依据的决定和恢复本文写法的时点，过渡期满按本文执行）；不能改变本文的需求内容；需要改变时按 §14 提出变更。
4. 设计文档与任务卡不得与以上冲突。
